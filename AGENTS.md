# AGENTS.md

Blazor Server (.NET 10) app — a local Ollama chat + LLM benchmark lab using FluentUI Blazor v4.14.2, Dapper, SQLite, Serilog. UI text and code comments are in Portuguese (PT). Single app project + a unit-test project; no lint/format config. The Ollama HTTP API is consumed directly via `HttpClient` + `System.Text.Json` — there is **no OllamaSharp and no HTML parsing package** (both were removed as dead dependencies; do not reintroduce them without a real need).

## Build status (important)

The solution builds as a **single app project** (`OllamaArena/`) plus a **test project** (`OllamaArena.Tests/`, xUnit). The root `Services/` folder (a stale, abandoned refactor with broken namespaces `MediaOrganizerApp.WebApi.Services`) was **removed**; the slnx only references `OllamaArena/` and `OllamaArena.Tests/`. If a `Services/Services.csproj` ever reappears, do not "fix" it — the live service layer is `OllamaArena/Services/` (namespaces `OllamaArena.Services.*`), wired up in `Program.cs`.

## Commands

- Run: `dotnet watch run` from `OllamaArena/`. The **implicit** launch profile is `http` → `http://localhost:5292`; the `https` profile (`https://localhost:7175`) is only used when you pass `--launch-profile https` explicitly.
- Build: `dotnet build OllamaArena.slnx` (solution uses the new XML `.slnx` format).
- Test: `dotnet test OllamaArena.slnx` (257 tests in 20 classes; no test count guarantees, so don't hardcode a number).
- CI: `.github/workflows/deploy-iis.yml` publishes Release and deploys to the author's self-hosted IIS runner (port 4800); not relevant on other machines.
- Verification: successful build + passing tests + manual run.

## Git & commits

- **Never commit automatically** — after changing code, the agent must not run `git add`, `git commit` or `git push` on its own initiative; the working tree stays ready for the author to review and commit. Commits are only allowed when the author **explicitly asks** during a session (pushes likewise).
- Agent workflow after finishing code changes: run `dotnet build OllamaArena.slnx` + `dotnet test OllamaArena.slnx`, report what changed (read-only `git status`/`git diff`), and stop — leaving the working tree ready for the author to review and commit.
- On request, the agent may propose a commit message in Portuguese (PT), concise, matching the existing history style.

## Execution plan on disk (credit-loss backup)

- **Any non-trivial change must get its plan written to `Docs/plan-<slug>.md` *before* the first edit.** The trigger is the number of steps, not the number of files: a plan is required as soon as the task needs more than one round of tool calls, or more than one edit→verify cycle — whether it touches one file or ten. The only exemption is a single-file, single-edit, unambiguous change (e.g. appending a section to this file). Without that plan an interrupted session (out of credits, crash, context loss) leaves no on-disk trace of what was done, and the next session has to re-derive it from the conversation. Precedent: `Docs/code-review.md`, required by the profile in `Docs/Ollama_CodeReviewer.md`.
- The plan is the resume point, so it must contain: the goal in one line; the exact list of files to change; a checklist of steps each tagged `pendente` / `feito` / `parcial`; and the verification command (`dotnet build OllamaArena.slnx` + `dotnet test OllamaArena.slnx`).
- **Update it as the work progresses.** A step only becomes `feito` after the build **and** the tests pass; anything half-done is `parcial` with a note on what is missing. The last section always states explicitly what is left to do.
- At the start of a session, unfinished `Docs/plan-*.md` files are the source of truth: read them first and continue from the last `feito` step instead of starting over.
- Once everything is `feito` and verified, the agent **deletes the `Docs/plan-*.md` file it created** (scaffolding, not a deliverable). `Docs/code-review.md` is a deliverable of the code-review profile and is never auto-deleted.

## Runtime requirements

- Ollama daemon must be running (`ollama serve`); the app hardcodes `http://localhost:11434` (chat, translation, and keep-alive unload requests in `Chat.razor.cs`).
- No migrations: the SQLite schema is created lazily. DB lives at `OllamaArena/ollama_benchmark.db` (path from `appsettings.json` `SqliteConnection`, resolved against `ContentRootPath`). Serilog's SQLite sink writes to the same DB/table `Logs`. There are **7 tables** (`Prompts`, `Respostas`, `Conversas`, `ConversaMensagens`, `Configuracoes`, `ModelosJuiz`, `Logs`); `Docs/schema.sql` mirrors that exact set.

## State & persistence gotchas

- `ollama_benchmark.db` is **not tracked** (gitignored along with `-shm`/`-wal`/`-journal` and `*.sqbpro`). The schema is created lazily on first run, so a fresh clone starts with an empty DB.
- Model list, selected model, and theme persist in browser **localStorage**, not the DB: keys `ollamaModels`, `ollama_model`, `theme`. New models only appear after `ollama pull <tag>` (the `ollamaModels` cache is refreshed by the Chat/Home pages). The enriched model list lives under `ollamaModelsFullV2` (v1 `ollamaModelsFull` is dead: it lacked the `SupportsThinking` field; Home still removes both when clearing the per-session cache).
- **Auto-save with SUMMARY**: after streaming completes, the model's response is parsed for a `SUMMARY: <3-5 word description>` marker (via `ChatComposerService.ExtractSummaryFromResponse()`). If absent, `SmartFallbackDescription()` extracts the first meaningful sentence (up to first `.` or newline), truncated at word boundary to 50 chars. The conversation is then **auto-saved immediately** (no ConfirmSaveDialog). The `ChatMessage` entity has a `Summary` property.
- **Judge settings** (Gemini/OpenRouter API keys, OpenRouter judge model) are configurable via the **Settings page** and persist in the DB table `Configuracoes` (key/value). Resolution priority in `AutomatedJudgeService`: **DB → configuration (user-secrets/appsettings) → defaults**. Keys can still be provided pre-publish via user-secrets `ApiKeys:Gemini`/`ApiKeys:OpenRouter` as fallback. The Settings save button is dirty-tracked and requires a confirmation dialog (summary of changes; keys are shown only as set/removed, never their value). The judge temperature is **fixed at 0** (deterministic; not configurable).
- The **reasoning (think)** toggle on the Settings page persists as `Chat:EnableReasoning` in `Configuracoes`; default is **false**. `ChatComposerService.Prepare` (async) resolves it itself with priority **DB → `OllamaOptions.EnableReasoning` config → default false** and, for models that support the `thinking` capability (via `/api/show`), sends the `think` value **explicitly** (`true`/`false`) — omitting the field makes Ollama think by default and return reasoning even when disabled; the field is omitted entirely for non-thinking models (Ollama returns 400 "does not support thinking"). When disabled, reasoning is **not captured/persisted/displayed** either (`PreparedChatRequest.EnableReasoning` gates the `Reasoning` capture in `Chat.razor.cs`) — models like `deepseek-r1` always generate thinking and ignore `think: false`.
- **Reasoning capability per model:** `OllamaGpuService.GetExtendedModelMetadataAsync` returns a `ModelExtendedMetadata` record (`ContextLength`, `TrainingYear`, `SupportsThinking`) read from a **single** `/api/show` call (no extra HTTP request for the capability). `ModelSupportsThinkingAsync` stays as the Chat's on-demand check. `SupportsThinking` is `bool?`: `null` means **unknown** (older Ollama that doesn't return the `capabilities` array) and is never confused with "not supported"; it feeds the "Raciocínio" badge on `/modelos-ollama` and is cached in `ollamaModelsFullV2`. The page also has a sticky `.toolbar` (same markup/CSS pattern as `/benchmark-evaluations`) whose **"O que significa cada coluna?"** button opens `ModelColumnsInfoDialog` (600px; `width: min(600px, 95vw)`, scrollable body) — a 9-section explainer, one per grid column and in the same order (Nome, Família, Parâmetros, Quantização, Ano de Treino, Contexto Máximo, Tamanho no Disco, Raciocínio, Compatibilidade GPU) mirroring `GpuInfoDialog`; its text lives in the `Modelos.Help*` resources (PT + EN), which must never ship an empty `<value />` — an empty resource renders as a blank paragraph or a stray empty bullet in the dialog.
- The **Settings page** picks the OpenRouter judge model from the **live OpenRouter catalog** (`OpenRouterCatalogService` → `GET https://openrouter.ai/api/v1/models`, free models only) via a **radio-button list** (`openrouter/free` is always pinned at the top), with a manual-ID fallback field for offline/custom IDs. The active model is stored in `Configuracoes` (`AutomatedJudge:OpenRouterModel`). The legacy `ModelosJuiz` table/seed is kept for compatibility but no longer used by the UI.
- **Judge origin is persisted, not assumed:** `Respostas.Juiz1Origem`/`Juiz2Origem` hold `gemini` / `openrouter` / `externo` / `NULL` (manual paste or no answer), resolved by `Services/Helpers/JudgeOriginResolver.cs` and rendered by `JudgeLabelResolver`. The evaluation dialog labels must use those helpers — never hardcode "Gemini"/"OpenRouter" for a slot that was filled by hand. The columns are added by the `DatabaseSchemaInitializer` migration (`PRAGMA table_info`).
- **Translation chain:** judge-feedback translation prefers **OpenRouter → Gemini → Ollama (local)**. The button is disabled when `Prompts/translation-prompt.txt`-based detection proves the text is already in the UI language; while running, the UI shows the provider in use, the elapsed time and a cancel action.
- **Web search is gone:** there is no `HtmlAgilityPack`, no `_webSearchEnabled` and no `BuscarContextoWebAsync`. Do not reintroduce scraping without an explicit request.

## Prompts

- `Prompts/*.txt` are `Content` files copied to output (`CopyToOutputDirectory=Always`); editable at runtime via the "EditPromptFiles" page. `PromptTemplates/` holds C# prompt builders.
- `PromptFilesService` also serves two **read-only** document folders, each with PT + `.en.md` variants resolved from the UI language: `PlanoDeTestes/` (`/plano-de-testes`) and `ComoCompararModelos/` (`/comparar-modelos`). Both pages go through `wwwroot/js/markdown-anchors.js` for smooth anchor scrolling.
- There is **no `SystemPromptService`**: `Chat.razor.cs` reads `Prompts/system-prompt.txt` directly via `PromptFilesService` and combines it with `PromptTemplates/ChatInstructionsPrompt.cs`.
- `Models/DTO` vs `Models/Entities`: DTOs are API shapes; Entities map to SQLite tables via Dapper.
- **Benchmark persistence is split by responsibility** (was one ~850-line `BenchmarkRepository`): `IBenchmarkCommandRepository`/`BenchmarkCommandRepository` (writes), `IBenchmarkQueryRepository`/`BenchmarkQueryRepository` (read models for the evaluations grid, history panel and prompt detail) and `IBenchmarkStatsRepository`/`BenchmarkStatsRepository` (dashboard, timeline, ranking, chart series — the only one taking `IOptions<JudgeScoreWeights>`). All three are `AddScoped` over the same `IDapperContext`; **inject the narrow one a consumer actually needs** (e.g. `TranslationService` only wants `GetBestModelAsync`).
- **`.xlsx` export never goes through SignalR as base64**: `BenchmarkExcelExporter.GerarAsync` writes `%TEMP%/ollamaarena-exports/{Guid:N}.xlsx` and returns the identifier; `BenchmarkEvaluations.razor` then calls `downloadBenchmarksExcel` (`wwwroot/js/excel.js`), which fetches `GET /api/export/benchmarks/{identificador}` (`Program.cs`). The file is deleted in `HttpContext.Response.OnCompleted`, older-than-1h files are swept on each export, and `BenchmarkExcelExporter.ResolverCaminho` rejects anything that is not a Guid "N" (so a crafted id can never escape the temp folder).
- **The local analysis report is data, not HTML:** `BenchmarkAnalysisResult.LinhasAnaliseDetalhada` is `List<BenchmarkAnalysisLine>` (`Rotulo` + plain `Texto`). `LocalAnalysisService` splits the localized resources with `BenchmarkAnalysisLine.Criar` and `BenchmarkAnalysisViewer` renders the label in `<strong>` and escapes the rest — so a model name from the DB is displayed literally and **no `MarkupString`/sanitizer is involved**. `HtmlOutputSanitizer` remains only for the static `AnalysisViewer.ReadyHint`.

## Conventions

- Deterministic LLM tuning: temperature ~0.3, `repeat_penalty` 1.1 (see `Chat.razor.cs` `ChatMeasureTemperature`).
- Blazor: buttons inside clickable cards need `@onclick:stopPropagation` (per README) to avoid cascading events.
- **Page titles are shared:** use `<PageHeader Title="..." [Subtitle="..."] />` (`OllamaArena/Components/Pages/Components/PageHeader.razor`) for the visible page heading — never duplicate the gradient/divider CSS per page. Dark theme is the CSS base (`#38BDF8 → #A78BFA`); the light variant (`#0284C7 → #7C3AED`) is keyed off `body[data-theme="light"]` (set by `FluentDesignTheme` in `MainLayout.razor`). `<PageTitle>` remains separate (browser tab). Currently used in Settings, SystemLogs, ModelosOllama, Dashboard, `/benchmarks` and `/benchmark-evaluations`.
- **PDF export embeds fonts:** the benchmark-evaluation report (`OllamaArena/wwwroot/js/pdf.js`, called from `BenchmarkEvaluations.razor.cs` `ExportarParaPdfAsync`) must never rely on the PDF standard fonts for real content. They measure with an approximation table (helvetica gives every out-of-coverage char the same generic width; courier measures everything at 0.6 em), so wrapping does not match the glyphs actually drawn and lines escape the right margin. It embeds `OllamaArena/wwwroot/fonts/Inter-{Regular,Bold}.ttf` (text) and `RobotoMono-Regular.ttf` (prompt), fetched from `fonts/` via `document.baseURI` and cached in base64, and **degrades to `helvetica`/`courier` if the fetch fails** — never throw. All text passes through `normalizarTextoPdf` (NFC, exotic spaces → space, arrows/✓/† → ASCII, invisibles dropped, anything outside the fonts' latin subset dropped) and paragraphs are **paginated line by line** (`novaPaginaSeNecessario` before every `doc.text`). When swapping fonts, re-check the `CARACTERES_COBERTOS` allowlist against the TTF `cmap` tables; `OllamaArena/wwwroot/fonts/NOTICE.md` + `OFL.txt` document provenance and licence (SIL OFL 1.1).
- **JS interop files** live in `wwwroot/js/`: `clipboard.js` (`window.copyToClipboard`), `conversations.js` (`window.conversations` — `downloadJson` / `pickJsonFile` for conversation JSON export/import), `markdown-anchors.js` (no global, capture-phase `stopPropagation` is what keeps Blazor from treating anchors as SPA navigation) and `pdf.js`.
